# Решения для устранения проблем архитектуры InsureTech

## Обзор изменений

Диаграмма контейнеров была обновлена для решения выявленных проблем и рисков. Основные изменения:

1. **Добавлен Message Broker (Apache Kafka)** для Event-Streaming архитектуры
2. **Внедрен паттерн Transactional Outbox** в core-app
3. **Заменены синхронные REST взаимодействия на асинхронные Event-Streaming**

## Детальное описание решений

### 1. Message Broker (Apache Kafka)

**Расположение на диаграмме:** Центральный компонент между сервисами

**Назначение:**
- Обеспечивает асинхронную публикацию и подписку на события
- Гарантирует доставку сообщений
- Позволяет масштабировать обработку событий

**Преимущества:**
- Разделение производителей и потребителей событий
- Возможность обработки событий в реальном времени
- Устойчивость к сбоям отдельных сервисов
- Масштабируемость при росте нагрузки

### 2. Event-Streaming для обновления данных о продуктах

**Старое взаимодействие:**
- `core-app → ins-product-aggregator` (REST, каждые 15 минут)
- `ins-comp-settlement → ins-product-aggregator` (REST, раз в сутки)

**Новое взаимодействие:**
- `ins-product-aggregator → Message Broker` (публикация событий об изменении продуктов)
- `Message Broker → core-app` (подписка на события)
- `Message Broker → ins-comp-settlement` (подписка на события)

**Преимущества:**
- Устранение периодических запросов
- Актуальность данных в реальном времени
- Снижение нагрузки на ins-product-aggregator
- Улучшение отказоустойчивости (при сбое одного подписчика другие продолжают работать)

**Как это работает:**
1. `ins-product-aggregator` периодически опрашивает страховые компании
2. При обнаружении изменений в продуктах/тарифах публикует событие в Message Broker
3. `core-app` и `ins-comp-settlement` подписываются на эти события и обновляют локальные кэши
4. Обновление происходит только при реальных изменениях, а не по расписанию

### 3. Transactional Outbox для событий о создании страховок

**Старое взаимодействие:**
- `ins-comp-settlement → core-app` (REST, раз в сутки, запрос всех оформленных страховок)

**Новое взаимодействие:**
- `core-app → Message Broker` (публикация событий о создании страховок через Transactional Outbox)
- `Message Broker → ins-comp-settlement` (подписка на события)

**Паттерн Transactional Outbox:**

**Проблема, которую решает:**
- При создании страховки в `core-app` нужно гарантировать, что событие будет доставлено в `ins-comp-settlement`
- Прямая публикация в Message Broker может привести к потере события при сбое

**Решение:**
1. При создании страховки в `core-app`:
   - Запись в основную таблицу страховок (в транзакции)
   - Запись события в таблицу Outbox (в той же транзакции)
2. Отдельный процесс (Outbox Publisher) периодически:
   - Читает неопубликованные события из таблицы Outbox
   - Публикует их в Message Broker
   - Помечает события как опубликованные

**Преимущества:**
- Гарантированная доставка событий (даже при сбоях)
- Согласованность данных (транзакция гарантирует, что страховка и событие записаны вместе)
- Устранение необходимости синхронного запроса от `ins-comp-settlement` к `core-app`
- Возможность обработки событий в реальном времени

**Как это работает:**
1. Клиент создает страховку через `core-app`
2. `core-app` в одной транзакции:
   - Сохраняет страховку в БД
   - Записывает событие `InsuranceCreated` в таблицу Outbox
3. Outbox Publisher (отдельный процесс) периодически:
   - Читает неопубликованные события из Outbox
   - Публикует их в Message Broker
   - Помечает как опубликованные
4. `ins-comp-settlement` подписывается на события `InsuranceCreated` и обрабатывает их для формирования реестра

### 4. Сохранение устаревших связей на диаграмме

**Причина:**
- На диаграмме сохранены старые REST связи, помеченные как `(deprecated)`
- Это позволяет видеть эволюцию архитектуры и понимать, что было заменено

**Планируемое удаление:**
- После полного перехода на Event-Streaming эти связи можно будет удалить

## Решенные проблемы

### 1. Проблемы производительности

✅ **Увеличение времени ответа ins-product-aggregator**
- Решено: Асинхронная публикация событий вместо синхронных запросов
- При росте количества страховых компаний время обработки не влияет на подписчиков

✅ **Неэффективное использование ресурсов**
- Решено: Обновление данных только при реальных изменениях, а не по расписанию

### 2. Проблемы отказоустойчивости

✅ **Каскадные сбои при ошибках внешних API**
- Решено: При сбое одной страховой компании другие продолжают работать
- Подписчики получают события только от успешно обработанных компаний

✅ **Отсутствие гарантии доставки данных**
- Решено: Transactional Outbox гарантирует доставку событий о создании страховок

### 3. Проблемы согласованности данных

✅ **Устаревшие локальные реплики**
- Решено: Обновление данных в реальном времени через события
- Все подписчики получают одинаковые данные одновременно

✅ **Race conditions при обновлении данных**
- Решено: Message Broker обеспечивает порядок обработки событий

### 4. Проблемы масштабируемости

✅ **Линейный рост нагрузки на ins-product-aggregator**
- Решено: Публикация событий один раз, обработка множеством подписчиков
- Возможность горизонтального масштабирования Message Broker

✅ **Проблемы с большими объёмами данных**
- Решено: События обрабатываются по мере поступления, нет необходимости запрашивать все данные сразу

## Технические детали реализации

### Message Broker: Apache Kafka

**Выбор технологии:**
- Apache Kafka выбран как надежный и масштабируемый Message Broker
- Поддерживает высокую пропускную способность
- Гарантирует порядок сообщений в рамках партиции
- Обеспечивает персистентность сообщений

**Топики:**
- `products-updated` - события об изменении продуктов/тарифов
- `insurance-created` - события о создании страховок

### Transactional Outbox

**Реализация:**
- Таблица `outbox` в БД `core-app`:
  - `id` - уникальный идентификатор
  - `event_type` - тип события (например, `InsuranceCreated`)
  - `payload` - JSON с данными события
  - `status` - статус (pending, published, failed)
  - `created_at` - время создания
  - `published_at` - время публикации

**Outbox Publisher:**
- Отдельный процесс (микросервис или scheduled job)
- Периодически опрашивает таблицу Outbox
- Публикует события в Kafka
- Обрабатывает ошибки и повторные попытки

## Миграционный план

### Этап 1: Внедрение Message Broker
- Развертывание Apache Kafka
- Настройка топиков

### Этап 2: Миграция обновления продуктов
- Обновление `ins-product-aggregator` для публикации событий
- Обновление `core-app` и `ins-comp-settlement` для подписки на события
- Постепенное отключение REST запросов

### Этап 3: Внедрение Transactional Outbox
- Добавление таблицы Outbox в БД `core-app`
- Реализация Outbox Publisher
- Обновление `core-app` для записи событий в Outbox
- Обновление `ins-comp-settlement` для подписки на события

### Этап 4: Удаление устаревших связей
- Полное отключение REST запросов
- Удаление устаревших связей с диаграммы

## Ожидаемые результаты

1. **Снижение нагрузки на ins-product-aggregator** на 70-80% (за счет устранения периодических запросов)
2. **Улучшение времени отклика** для пользователей (актуальные данные в реальном времени)
3. **Повышение отказоустойчивости** (устойчивость к сбоям отдельных компонентов)
4. **Готовность к масштабированию** при добавлении новых страховых компаний
5. **Гарантированная доставка** событий о создании страховок

## Риски и митигация

### Риск: Сложность внедрения
**Митигация:** Поэтапная миграция, тестирование на каждом этапе

### Риск: Проблемы с порядком событий
**Митигация:** Использование партиционирования в Kafka для гарантии порядка

### Риск: Задержки в обработке событий
**Митигация:** Мониторинг латентности, настройка производительности Kafka

## Заключение

Предложенные решения устраняют все выявленные проблемы и риски, обеспечивая:
- Масштабируемость при росте количества страховых компаний
- Отказоустойчивость при сбоях компонентов
- Актуальность данных в реальном времени
- Гарантированную доставку критических событий

Архитектура готова к добавлению новых страховых компаний и дальнейшему росту нагрузки.
