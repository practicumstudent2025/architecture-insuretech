# Анализ текущей архитектуры InsureTech

## Выявленные проблемы и риски

### 1. Проблемы производительности

#### 1.1. Увеличение времени ответа ins-product-aggregator
- **Проблема**: При росте количества страховых компаний с 5 до 10 время агрегации данных увеличится пропорционально
- **Влияние**: Увеличение времени ответа для core-app, блокировка процесса формирования реестра в ins-comp-settlement, потенциальные таймауты

#### 1.2. Неэффективное использование ресурсов
- **Проблема**: core-app запрашивает данные каждые 15 минут, даже если изменения не произошли
- **Влияние**: Избыточная нагрузка на ins-product-aggregator и внешние API страховых компаний

#### 1.3. Линейный рост времени обработки
- **Проблема**: При последовательных запросах время обработки = сумма времени всех запросов
- **Влияние**: При 10 компаниях общее время может достигать 5 секунд, пользователи видят задержки

### 2. Проблемы отказоустойчивости

#### 2.1. Каскадные сбои при ошибках внешних API
- **Проблема**: Если одна из страховых компаний недоступна, весь процесс агрегации может завершиться неудачей
- **Влияние**: core-app не получает данные, ins-comp-settlement не может сформировать реестр, пользователи видят устаревшие данные

#### 2.2. Отсутствие гарантии доставки данных
- **Проблема**: При сбое запроса от ins-comp-settlement к core-app данные об оформленных страховках могут быть потеряны
- **Влияние**: Невозможность формирования полного реестра для взаиморасчётов, финансовые потери

#### 2.3. Зависимость от доступности всех страховых компаний
- **Проблема**: При недоступности хотя бы одной компании блокируется весь процесс
- **Влияние**: Полная остановка обновления данных о продуктах

### 3. Проблемы согласованности данных

#### 3.1. Устаревшие локальные реплики
- **Проблема**: Локальные кэши в core-app и ins-comp-settlement обновляются с разной частотой (15 минут vs 24 часа)
- **Влияние**: Несогласованность данных между сервисами, пользователи видят разные тарифы

#### 3.2. Отсутствие единого источника истины
- **Проблема**: Данные хранятся в нескольких местах без синхронизации
- **Влияние**: Расхождение данных между сервисами, сложность отладки

### 4. Проблемы масштабируемости

#### 4.1. Линейный рост нагрузки
- **Проблема**: При добавлении новых страховых компаний нагрузка растёт линейно
- **Влияние**: Необходимость горизонтального масштабирования, увеличение инфраструктурных затрат

#### 4.2. Проблемы с большими объёмами данных
- **Проблема**: Запрос всех оформленных страховок за день может стать проблематичным при росте бизнеса
- **Влияние**: Таймауты, перегрузка сети, невозможность формирования реестра

#### 4.3. Ограничения синхронной обработки
- **Проблема**: Синхронные запросы блокируют выполнение до получения ответа
- **Влияние**: Снижение пропускной способности системы

## Риски при росте нагрузки

### Краткосрочные риски (при добавлении 5 новых компаний):

1. **Увеличение времени ответа в 2 раза** - с ~2.5 секунд до ~5 секунд
2. **Увеличение вероятности сбоев** - с ~5% до ~10%
3. **Рост нагрузки на сеть и CPU** ins-product-aggregator
4. **Проблемы с таймаутами** при медленных ответах от новых компаний

### Долгосрочные риски:

1. **Невозможность масштабирования** текущей архитектуры
2. **Рост технического долга** из-за обходных решений
3. **Проблемы с производительностью** при дальнейшем росте
4. **Увеличение стоимости инфраструктуры**

## Критические точки отказа

1. **ins-product-aggregator** - единая точка отказа для получения данных о продуктах
2. **Синхронные запросы к страховым компаниям** - блокируют весь процесс при сбое одной компании
3. **Периодические запросы** - создают пиковые нагрузки в определенное время
4. **Отсутствие механизма очередей** - нет буферизации запросов
