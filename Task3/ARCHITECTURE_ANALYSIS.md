# Анализ текущей архитектуры InsureTech

## Текущая архитектура

### Взаимодействия между сервисами:

1. **core-app → ins-product-aggregator** (REST API)
   - Запрос данных о продуктах и тарифах
   - Частота: каждые 15 минут
   - Локальное кэширование данных в core-app

2. **ins-comp-settlement → ins-product-aggregator** (REST API)
   - Запрос данных о продуктах и тарифах
   - Частота: раз в сутки (ночью)
   - Локальное кэширование данных в ins-comp-settlement

3. **ins-comp-settlement → core-app** (REST API)
   - Запрос всех оформленных страховок за день
   - Частота: раз в сутки
   - Используется для формирования реестра

4. **ins-product-aggregator → Системы страховых компаний** (REST/SOAP/GraphQL)
   - Синхронные запросы ко всем страховым компаниям
   - Текущее количество: 5 компаний
   - Планируется: +5 компаний (всего 10)

## Выявленные проблемы и риски

### 1. Проблемы производительности

#### 1.1. Увеличение времени ответа ins-product-aggregator
- **Проблема**: При росте количества страховых компаний с 5 до 10, время агрегации данных увеличится пропорционально
- **Риск**: Синхронные запросы ко всем компаниям последовательно или параллельно создают узкое место
- **Влияние**: 
  - Увеличение времени ответа для core-app (каждые 15 минут)
  - Блокировка процесса формирования реестра в ins-comp-settlement (раз в сутки)
  - Потенциальные таймауты при медленных ответах от страховых компаний

#### 1.2. Неэффективное использование ресурсов
- **Проблема**: core-app запрашивает данные каждые 15 минут, даже если изменения не произошли
- **Риск**: Избыточная нагрузка на ins-product-aggregator и внешние API страховых компаний
- **Влияние**: Рост нагрузки при увеличении количества компаний

### 2. Проблемы отказоустойчивости

#### 2.1. Каскадные сбои при ошибках внешних API
- **Проблема**: Если одна из страховых компаний недоступна или отвечает с ошибкой, весь процесс агрегации может завершиться неудачей
- **Риск**: 
  - core-app не получает актуальные данные о продуктах
  - ins-comp-settlement не может сформировать реестр
  - Пользователи видят устаревшие или неполные данные
- **Влияние**: Критично при росте количества компаний (вероятность сбоя хотя бы одной увеличивается)

#### 2.2. Отсутствие гарантии доставки данных
- **Проблема**: При сбое запроса от ins-comp-settlement к core-app данные об оформленных страховках могут быть потеряны
- **Риск**: Невозможность формирования полного реестра для взаиморасчётов
- **Влияние**: Финансовые потери, проблемы с отчётностью

### 3. Проблемы согласованности данных

#### 3.1. Устаревшие локальные реплики
- **Проблема**: Локальные кэши в core-app и ins-comp-settlement обновляются с разной частотой (15 минут vs 24 часа)
- **Риск**: Несогласованность данных между сервисами
- **Влияние**: 
  - Пользователи могут видеть разные тарифы в разных частях системы
  - Проблемы при формировании реестра с устаревшими данными

#### 3.2. Race conditions при обновлении данных
- **Проблема**: При одновременном запросе от нескольких сервисов возможны конфликты
- **Риск**: Некорректное состояние данных
- **Влияние**: Ошибки в бизнес-логике

### 4. Проблемы масштабируемости

#### 4.1. Линейный рост нагрузки на ins-product-aggregator
- **Проблема**: При добавлении новых страховых компаний нагрузка растёт линейно
- **Риск**: Необходимость горизонтального масштабирования сервиса
- **Влияние**: Увеличение инфраструктурных затрат

#### 4.2. Проблемы с большими объёмами данных
- **Проблема**: Запрос всех оформленных страховок за день от core-app к ins-comp-settlement может стать проблематичным при росте бизнеса
- **Риск**: Таймауты, перегрузка сети, проблемы с памятью
- **Влияние**: Невозможность формирования реестра при больших объёмах

### 5. Проблемы мониторинга и отладки

#### 5.1. Сложность отслеживания проблем
- **Проблема**: При синхронных взаимодействиях сложно определить источник проблемы
- **Риск**: Долгое время восстановления после сбоев
- **Влияние**: Увеличение MTTR (Mean Time To Recovery)

#### 5.2. Отсутствие истории изменений
- **Проблема**: Нет возможности отследить, когда и какие данные были обновлены
- **Риск**: Сложность аудита и отладки
- **Влияние**: Проблемы с соответствием требованиям и расследованием инцидентов

## Риски при росте нагрузки

### Краткосрочные риски (при добавлении 5 новых компаний):

1. **Увеличение времени ответа в 2 раза** (при последовательных запросах)
2. **Увеличение вероятности сбоев** (больше точек отказа)
3. **Рост нагрузки на сеть и CPU** ins-product-aggregator
4. **Проблемы с таймаутами** при медленных ответах от новых компаний

### Долгосрочные риски:

1. **Невозможность масштабирования** текущей архитектуры
2. **Рост технического долга** из-за обходных решений
3. **Проблемы с производительностью** при дальнейшем росте
4. **Увеличение стоимости инфраструктуры** из-за неэффективного использования ресурсов

## Рекомендации по решению

### 1. Переход на Event-Streaming архитектуру

**Для обновления данных о продуктах:**
- ins-product-aggregator публикует события об изменении продуктов/тарифов
- core-app и ins-comp-settlement подписываются на эти события
- Обновление данных происходит асинхронно при реальных изменениях

**Преимущества:**
- Устранение периодических запросов
- Актуальность данных в реальном времени
- Снижение нагрузки на ins-product-aggregator
- Улучшение отказоустойчивости

### 2. Использование паттерна Transactional Outbox

**Для гарантированной доставки событий:**
- При создании страховки в core-app событие записывается в outbox таблицу в той же транзакции
- Отдельный процесс публикует события из outbox в message broker
- Гарантируется доставка событий даже при сбоях

**Преимущества:**
- Гарантия доставки событий о создании страховок
- Согласованность данных между сервисами
- Устранение необходимости синхронного запроса от ins-comp-settlement к core-app

### 3. Асинхронная обработка запросов к страховым компаниям

**Для ins-product-aggregator:**
- Асинхронная обработка запросов к страховым компаниям
- Использование паттернов Circuit Breaker и Retry
- Кэширование результатов с TTL

**Преимущества:**
- Устойчивость к сбоям отдельных компаний
- Улучшение производительности
- Возможность обработки запросов в фоне

### 4. Оптимизация взаимодействий

**Устранение синхронных зависимостей:**
- Замена синхронного запроса ins-comp-settlement → core-app на события
- Использование Event Sourcing для истории изменений
- Внедрение CQRS для разделения чтения и записи

## Итоговая оценка

**Критичность проблем:** Высокая
**Необходимость изменений:** Критическая
**Сроки внедрения:** Рекомендуется до добавления новых страховых компаний

Текущая архитектура не готова к масштабированию и требует рефакторинга с переходом на Event-Driven архитектуру.
