# Анализ текущей архитектуры InsureTech

## Выявленные проблемы и риски

### 1. Проблемы производительности

#### 1.1. Увеличение времени ответа ins-product-aggregator
- **Проблема**: При росте количества страховых компаний с 5 до 10 время агрегации данных увеличится пропорционально
- **Влияние**: Увеличение времени ответа для core-app, блокировка процесса формирования реестра в ins-comp-settlement, потенциальные таймауты
- **Решение**: Переход на Event-Streaming архитектуру. ins-product-aggregator публикует события об изменении продуктов в Message Broker (Kafka). Сервисы core-app и ins-comp-settlement подписываются на эти события и обновляют локальные кэши асинхронно. Это устраняет необходимость периодических запросов и позволяет обрабатывать изменения в реальном времени.

#### 1.2. Неэффективное использование ресурсов
- **Проблема**: core-app запрашивает данные каждые 15 минут, даже если изменения не произошли
- **Влияние**: Избыточная нагрузка на ins-product-aggregator и внешние API страховых компаний
- **Решение**: При использовании Event-Streaming обновление данных происходит только при реальных изменениях. ins-product-aggregator опрашивает страховые компании в фоновом режиме и публикует события только при обнаружении изменений. Это значительно снижает нагрузку на систему.

#### 1.3. Линейный рост времени обработки
- **Проблема**: При последовательных запросах время обработки = сумма времени всех запросов
- **Влияние**: При 10 компаниях общее время может достигать 5 секунд, пользователи видят задержки
- **Решение**: Асинхронная обработка запросов к страховым компаниям в ins-product-aggregator с использованием паттернов Circuit Breaker и Retry. Параллельная обработка запросов к нескольким компаниям. При сбое одной компании остальные продолжают обрабатываться, обеспечивая частичную доступность данных.

### 2. Проблемы отказоустойчивости

#### 2.1. Каскадные сбои при ошибках внешних API
- **Проблема**: Если одна из страховых компаний недоступна, весь процесс агрегации может завершиться неудачей
- **Влияние**: core-app не получает данные, ins-comp-settlement не может сформировать реестр, пользователи видят устаревшие данные
- **Решение**: Внедрение механизма graceful degradation в ins-product-aggregator. При недоступности одной компании система продолжает работать с данными от доступных компаний. Использование Circuit Breaker для изоляции проблемных API. События публикуются для доступных данных, подписчики получают частичные обновления.

#### 2.2. Отсутствие гарантии доставки данных
- **Проблема**: При сбое запроса от ins-comp-settlement к core-app данные об оформленных страховках могут быть потеряны
- **Влияние**: Невозможность формирования полного реестра для взаиморасчётов, финансовые потери
- **Решение**: Использование паттерна Transactional Outbox в core-app. При создании страховки событие записывается в таблицу Outbox в той же транзакции, что и основная запись. Отдельный процесс (Outbox Publisher) публикует события из Outbox в Message Broker, гарантируя доставку даже при сбоях. ins-comp-settlement подписывается на события о создании страховок вместо периодических запросов.

#### 2.3. Зависимость от доступности всех страховых компаний
- **Проблема**: При недоступности хотя бы одной компании блокируется весь процесс
- **Влияние**: Полная остановка обновления данных о продуктах
- **Решение**: Реализация частичной обработки (graceful degradation). ins-product-aggregator обрабатывает запросы к доступным компаниям независимо, публикуя события для каждой компании отдельно. Подписчики получают обновления от доступных компаний, система продолжает работать частично.

### 3. Проблемы согласованности данных

#### 3.1. Устаревшие локальные реплики
- **Проблема**: Локальные кэши в core-app и ins-comp-settlement обновляются с разной частотой (15 минут vs 24 часа)
- **Влияние**: Несогласованность данных между сервисами, пользователи видят разные тарифы
- **Решение**: При переходе на Event-Streaming оба сервиса подписываются на одни и те же события об изменении продуктов. Обновление происходит одновременно для всех подписчиков при публикации события, обеспечивая согласованность данных в реальном времени.

#### 3.2. Отсутствие единого источника истины
- **Проблема**: Данные хранятся в нескольких местах без синхронизации
- **Влияние**: Расхождение данных между сервисами, сложность отладки
- **Решение**: Message Broker становится единым каналом распространения данных. ins-product-aggregator является источником истины для данных о продуктах, публикуя события в Message Broker. Все подписчики получают одинаковые данные, что упрощает отладку и поддержку.

### 4. Проблемы масштабируемости

#### 4.1. Линейный рост нагрузки
- **Проблема**: При добавлении новых страховых компаний нагрузка растёт линейно
- **Влияние**: Необходимость горизонтального масштабирования, увеличение инфраструктурных затрат
- **Решение**: Event-Streaming архитектура позволяет масштабировать обработку независимо. ins-product-aggregator публикует события один раз, а обработка распределяется между множеством подписчиков. Message Broker (Kafka) обеспечивает горизонтальное масштабирование и высокую пропускную способность.

#### 4.2. Проблемы с большими объёмами данных
- **Проблема**: Запрос всех оформленных страховок за день может стать проблематичным при росте бизнеса
- **Влияние**: Таймауты, перегрузка сети, невозможность формирования реестра
- **Решение**: Замена синхронного запроса на асинхронную обработку событий. core-app публикует события о создании страховок через Transactional Outbox. ins-comp-settlement подписывается на эти события и обрабатывает их по мере поступления, накапливая данные для формирования реестра. Это устраняет необходимость запрашивать все данные сразу.

#### 4.3. Ограничения синхронной обработки
- **Проблема**: Синхронные запросы блокируют выполнение до получения ответа
- **Влияние**: Снижение пропускной способности системы
- **Решение**: Переход на асинхронную обработку через Message Broker. Сервисы не блокируются ожиданием ответа, обработка происходит независимо. Это значительно повышает пропускную способность системы и позволяет обрабатывать больше запросов параллельно.

## Риски при росте нагрузки

### Краткосрочные риски (при добавлении 5 новых компаний):

1. **Увеличение времени ответа в 2 раза** - с ~2.5 секунд до ~5 секунд
2. **Увеличение вероятности сбоев** - с ~5% до ~10%
3. **Рост нагрузки на сеть и CPU** ins-product-aggregator
4. **Проблемы с таймаутами** при медленных ответах от новых компаний

### Долгосрочные риски:

1. **Невозможность масштабирования** текущей архитектуры
2. **Рост технического долга** из-за обходных решений
3. **Проблемы с производительностью** при дальнейшем росте
4. **Увеличение стоимости инфраструктуры**

## Критические точки отказа

1. **ins-product-aggregator** - единая точка отказа для получения данных о продуктах
2. **Синхронные запросы к страховым компаниям** - блокируют весь процесс при сбое одной компании
3. **Периодические запросы** - создают пиковые нагрузки в определенное время
4. **Отсутствие механизма очередей** - нет буферизации запросов

## Решение: Использование паттерна Transactional Outbox

**Решение: Будем использовать паттерн Transactional Outbox**

### Обоснование:

Паттерн Transactional Outbox необходим для гарантированной доставки событий о создании страховок из core-app в ins-comp-settlement. Это критически важно, так как потеря данных о страховках приводит к финансовым потерям и проблемам с отчётностью.

### Как это работает:

1. **При создании страховки в core-app:**
   - Запись страховки в основную таблицу БД (в транзакции)
   - Запись события `InsuranceCreated` в таблицу Outbox (в той же транзакции)
   - Гарантируется атомарность: либо обе записи успешны, либо обе откатываются

2. **Outbox Publisher (отдельный процесс):**
   - Периодически опрашивает таблицу Outbox на наличие неопубликованных событий
   - Публикует события в Message Broker (Kafka)
   - Помечает события как опубликованные после успешной публикации
   - Обрабатывает ошибки и повторяет попытки при сбоях

3. **ins-comp-settlement:**
   - Подписывается на события `InsuranceCreated` из Message Broker
   - Обрабатывает события по мере поступления
   - Накапливает данные для формирования реестра

### Преимущества:

- **Гарантированная доставка**: Даже при сбое Message Broker события сохраняются в Outbox и будут опубликованы после восстановления
- **Согласованность данных**: Транзакция гарантирует, что страховка и событие записаны вместе
- **Устранение синхронных зависимостей**: ins-comp-settlement больше не зависит от доступности core-app в момент формирования реестра
- **Обработка в реальном времени**: События обрабатываются по мере поступления, а не раз в сутки

### Альтернативы и почему они не подходят:

- **Прямая публикация в Message Broker**: Риск потери события при сбое между записью в БД и публикацией
- **Периодические запросы (текущее решение)**: Не гарантирует доставку при сбоях, создаёт пиковые нагрузки
- **Двухфазный коммит (2PC)**: Слишком сложен и медленен для данной задачи

### Вывод:

Transactional Outbox является оптимальным решением для гарантированной доставки критически важных событий о создании страховок, обеспечивая надёжность и согласованность данных в распределённой системе.
