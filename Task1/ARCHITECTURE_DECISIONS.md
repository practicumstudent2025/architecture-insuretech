# Архитектурные решения для InsureTech (Task 1)

## Анализ схемы и соответствие требованиям

### ✅ Выполненные требования

#### 1. Мультизонная архитектура
- **Реализовано**: Схема содержит две зоны доступности (AZ-1 и AZ-2)
- **Географическое распределение**: Обеспечивает обслуживание клиентов из разных регионов РФ
- **Изоляция отказов**: Полная изоляция между зонами

#### 2. Балансировка нагрузки
- **Geo Load Balancing**: Реализован на уровне входа в систему
- **Application Load Balancer (ALB)**: По одному в каждой зоне для распределения нагрузки внутри зоны
- **CDN**: Используется для статического контента и кэширования

#### 3. Kubernetes кластеры
- **Реализовано**: Отдельные Kubernetes кластеры в каждой зоне
- **Сервисы**: Все основные сервисы развернуты (core-app, client-info, ins-product-aggregator, ins-comp-settlement)

#### 4. Конфигурация базы данных
- **PostgreSQL кластеры**: По одному в каждой зоне
- **Primary/Replica**: В каждой зоне есть Primary и Replica для read scaling
- **Backup Storage**: Реализовано централизованное хранилище бэкапов

#### 5. B2B интеграция
- **API Gateway**: Отдельный API Gateway для партнеров/B2B клиентов
- **Изоляция трафика**: B2B трафик идет через отдельный путь

## Детальное описание архитектурных решений

### 1. Стратегия масштабирования и отказоустойчивости

#### Горизонтальное масштабирование
**Применяется для всех сервисов приложения:**
- Использование HPA (Horizontal Pod Autoscaler) для автоматического масштабирования
- Минимальное количество реплик для каждого сервиса:
  - `core-app`: 3+ реплики (критичный сервис)
  - `client-info`: 2+ реплики
  - `ins-product-aggregator`: 2+ реплики
  - `ins-comp-settlement`: 1+ реплика (низкая нагрузка)

**Преимущества:**
- Автоматическое масштабирование при росте нагрузки
- Высокая доступность при отказе отдельных подов
- Эффективное использование ресурсов

#### Вертикальное масштабирование
**Применяется для базы данных:**
- Увеличение ресурсов PostgreSQL при необходимости
- Масштабирование инстансов БД без изменения архитектуры приложения

#### Зоны безопасности
**Использованы 2 зоны доступности:**
- **AZ-1**: Первичная зона (например, Москва)
- **AZ-2**: Вторичная зона (например, Санкт-Петербург)

**Обоснование:**
- Обеспечение отказоустойчивости при падении одной зоны
- Географическое распределение для снижения латентности
- Соответствие требованиям RTO: 45 минут

---

### 2. Конфигурация развёртывания в Kubernetes

#### Решение: Независимые кластеры в каждой зоне

**Обоснование выбора:**

1. **Изоляция отказов**
   - При падении одного кластера второй продолжает работать независимо
   - Нет риска каскадных отказов между зонами
   - Каждый кластер управляется отдельно

2. **Независимое управление**
   - Упрощает обслуживание и обновления
   - Позволяет проводить работы в одной зоне без влияния на другую
   - Упрощает откат изменений

3. **Соответствие требованиям RTO**
   - При отказе одной зоны вторая готова к работе без дополнительной настройки
   - Минимальное время переключения

4. **Безопасность**
   - Изоляция снижает риск распространения проблем
   - Независимые политики безопасности

**Альтернатива (растянутый кластер) отклонена:**
- Требует низкой латентности между зонами (< 5ms)
- Сложнее в управлении и настройке
- Риск split-brain проблем
- Не обеспечивает полную изоляцию отказов

### 3. Балансировка нагрузки

#### Многоуровневая архитектура

**Уровень 1: Geo Load Balancing**
- **Функция**: Географическая балансировка между зонами
- **Механизм**: Распределение трафика на основе геолокации пользователя
- **Health Check**: 
  - Протокол: HTTP/HTTPS
  - Endpoint: `/health`
  - Interval: 10 секунд
  - Timeout: 5 секунд
  - Unhealthy threshold: 2 последовательных неудачных проверки
  - Healthy threshold: 2 последовательных успешных проверки
- **Алгоритм**: Round-robin с учетом health status и геолокации
- **Failover**: Автоматическое переключение на здоровую зону при отказе

**Уровень 2: Application Load Balancer (ALB) в каждой зоне**
- **Функция**: Балансировка внутри зоны между подами Kubernetes
- **Health Check**:
  - Endpoint: `/health`
  - Interval: 5 секунд
  - Timeout: 3 секунды
  - Unhealthy threshold: 2
- **Алгоритм**: Least connections для оптимального распределения
- **Session affinity**: Опционально для критичных операций

**Уровень 3: Kubernetes Service Load Balancing**
- **Функция**: Внутрикластерная балансировка
- **Readiness/Liveness Probes**: Автоматическое исключение нездоровых подов

**CDN (Content Delivery Network)**
- **Функция**: Распределение статического контента
- **Преимущества**:
  - Снижение нагрузки на backend
  - Одинаковое время загрузки для пользователей из разных регионов
  - Кэширование статического контента

**Health Checks на схеме:**
- Health checks должны быть явно отмечены на всех уровнях:
  - Между Geo Load Balancer и зонами
  - Между ALB и подами Kubernetes
  - Внутри Kubernetes для readiness/liveness probes

**Рекомендация**: Добавить на схему явные обозначения health checks на всех соединениях.

### 4. Фейловер-стратегия

#### Автоматический failover на уровне приложения

**Сценарий 1: Отказ Zone 1 (AZ-1)**
1. Geo Load Balancer обнаруживает недоступность AZ-1 через health check
2. Трафик автоматически переключается на AZ-2
3. Время переключения: < 30 секунд (зависит от настроек health check)
4. Пользователи продолжают работу без прерывания

**Сценарий 2: Отказ Master БД в Zone 1**
1. Система управления кластером БД (Patroni или аналогичная) обнаруживает недоступность Primary
2. Replica в той же зоне или Standby в другой зоне автоматически повышается до Primary
3. Приложения переключаются на новую Primary БД
4. RTO: 45 минут (включает время на проверку, переключение и валидацию)

**Сценарий 3: Частичный отказ (некоторые поды)**
1. Kubernetes автоматически перезапускает упавшие поды
2. Load Balancer исключает нездоровые поды из балансировки
3. HPA масштабирует оставшиеся поды при необходимости
4. Пользователи не замечают проблемы

**Механизм failover:**
- **Автоматическое обнаружение**: Health checks на всех уровнях
- **Автоматическое переключение**: Без вмешательства человека
- **Мониторинг**: Prometheus + Grafana для отслеживания состояния
- **Алертинг**: Уведомления команды при критичных событиях

**Рекомендация**: Добавить на схему явное описание фейловер-стратегии в виде комментария или аннотации.

### 5. Конфигурация базы данных

#### Архитектура БД

**Zone 1 (AZ-1) - Primary:**
- **PostgreSQL Primary**: Принимает все записи (write operations)
- **PostgreSQL Replica**: Для read-only запросов (read scaling)
- **Backup Storage**: Централизованное хранилище для бэкапов

**Zone 2 (AZ-2) - Secondary:**
- **PostgreSQL Primary**: Может стать активным при failover
- **PostgreSQL Replica**: Для read-only запросов в Zone 2
- **Backup Storage**: Доступ к централизованному хранилищу

#### Репликация данных

**Streaming Replication (PostgreSQL)**
- **Тип**: Синхронная репликация между зонами для обеспечения RPO: 15 минут
- **Механизм**: PostgreSQL Streaming Replication
- **Латентность**: < 1 секунда при нормальной работе
- **Надежность**: Гарантирует консистентность данных

**Управление кластером**
- **Фреймворк**: Patroni (рекомендуется) или аналогичный
- **Функции**:
  - Автоматическое обнаружение отказов
  - Автоматическое переключение Primary/Standby
  - Управление репликацией
  - Мониторинг состояния кластера
  - Конфигурация через Consul/etcd

**Рекомендация**: Добавить на схему указание использования Patroni или другого фреймворка для управления кластером БД.

#### Резервное копирование

**Стратегия бэкапов:**
- **Полные бэкапы**: Ежедневно в 02:00 (время минимальной нагрузки)
- **Инкрементальные бэкапы**: Каждые 15 минут
- **Хранение**: Yandex Object Storage (централизованное хранилище)
- **Retention Policy**: 
  - Последние 7 дней: ежедневные бэкапы
  - Последние 4 недели: еженедельные бэкапы
  - Последние 12 месяцев: ежемесячные бэкапы

**RPO обеспечение:**
- Инкрементальные бэкапы каждые 15 минут обеспечивают RPO: 15 минут
- Point-in-time recovery (PITR) для восстановления на любой момент времени
- Тестирование восстановления: еженедельно

**Рекомендация**: Добавить на схему явное указание частоты бэкапов и RPO.

### 6. Шардирование БД

#### Решение: Шардирование НЕ требуется

**Обоснование:**

1. **Объем данных**: 50 GB
   - PostgreSQL легко справляется с объемами до 1-2 TB на одном инстансе
   - Текущий объем не требует шардирования

2. **Сложность vs. выгода**
   - Шардирование добавляет значительную сложность:
     - Необходимость выбора ключа шардирования
     - Управление распределенными транзакциями
     - Сложность запросов, затрагивающих несколько шардов
     - Управление ребалансировкой данных
   - Выгода минимальна при текущем объеме данных

3. **Альтернативные решения**
   - Горизонтальное масштабирование через read replicas достаточно
   - Вертикальное масштабирование при необходимости
   - Оптимизация запросов и индексов

4. **Планы на будущее**
   - Если объем данных превысит 1 TB, можно рассмотреть шардирование
   - Возможные стратегии:
     - По клиентам (customer_id)
     - По типам данных (клиенты, продукты, заявки)
     - По датам (временное шардирование)
   - Использование решений типа Citus или аналогичных

**Рекомендация**: Добавить на схему комментарий о том, что шардирование не применяется, с кратким обоснованием.
